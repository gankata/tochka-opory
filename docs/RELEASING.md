# Выпуск новой версии

Этот документ — постоянный рабочий процесс релиза «Точки опоры». Его цель: предсказуемые обновления, понятные описания для пользователей и воспроизводимый архив для скачивания.

## 1. Соберите законченный пакет

В релиз включаются проверенные изменения с ясной пользовательской ценностью. Не нужно откладывать публикацию только из-за небольшого объёма кода или выпускать отдельный релиз для каждой промежуточной правки.

Перед выпуском:

- завершите заявленные сценарии и ручную проверку;
- убедитесь, что нет неучтённых изменений в рабочей копии;
- синхронизируйте локальный `main` с удалённым;
- не смешивайте релиз с несвязанной незавершённой работой.

## 2. Выберите номер по SemVer

Для текущей версии `X.Y.Z`:

- `Z` — исправления без новых возможностей;
- `Y` — новые обратно совместимые возможности и заметные улучшения;
- `X` — несовместимые изменения, требующие особой миграции.

Номер должен одинаково фигурировать в `package.json`, `package-lock.json`, git-теге и GitHub Release.

```bash
npm version X.Y.Z --no-git-tag-version
```

## 3. Обновите CHANGELOG.md

Используйте разделы «Добавлено», «Изменено», «Исправлено», «Удалено» и «Безопасность» только когда они содержат изменения. Описывайте наблюдаемый результат, а не перечисляйте каждый файл.

Добавьте ссылку сравнения с предыдущей версией. Не переносите в changelog рабочие обсуждения, промежуточные ошибки, локальные пути и внутренние идентификаторы задач.

## 4. Подготовьте описание для пользователей

Название: `Точка опоры X.Y.Z — короткая пользовательская выгода`.

Структура описания:

1. Одно вступительное предложение о главной ценности обновления.
2. Три–пять блоков с понятными заголовками и конкретным результатом.
3. Важные ограничения новой функции, если они влияют на использование.
4. Короткий раздел «Как обновиться».

Пишите на языке приложения. Не перегружайте текст коммитами, количеством тестов, названиями компонентов и служебными гарантиями процесса. Технические подробности остаются в changelog и истории git.

## 5. Проверьте изображения

Для заметных интерфейсных изменений подготовьте один–три коротких скриншота:

- показывайте только актуальную версию;
- используйте обобщённые демонстрационные записи;
- обрезайте изображение до полезной области;
- проверьте читаемость текста и отсутствие личных данных;
- сохраняйте оптимизированные изображения в `docs/images/`.

## 6. Выполните проверки

```bash
npm run check
npm run lint
npm test
npm run build
npm run test:browser
npm run check:performance
npm run check:windows
npm run check:public
git diff --check
```

Браузерные проверки должны подтверждать изменённые сценарии, мобильную ширину, клавиатуру, отсутствие ошибок консоли и неуспешных ответов. Используйте только изолированные тестовые данные.

## 7. Создайте коммиты и тег

Группируйте изменения по смыслу. Для небольшого согласованного пакета допустим один функциональный коммит; отдельный релизный коммит содержит версию, changelog и выпускающую документацию.

```bash
git add -A
git commit -m "chore(release): X.Y.Z"
git tag -a vX.Y.Z -m "Точка опоры X.Y.Z"
```

Не используйте `git add -f` для исключённых файлов. Перед коммитом просмотрите `git status --short` и состав индекса.

## 8. Соберите и проверьте архив

Создавайте архив именно из тега, чтобы его содержимое было воспроизводимым:

```bash
npm run package:release -- vX.Y.Z
```

Результат:

- `.release/tochka-opory.zip`;
- `.release/tochka-opory.zip.sha256`.

Имена файлов не меняются между версиями: постоянная ссылка `releases/latest/download/tochka-opory.zip` ведёт на последний релиз.

Распакуйте архив в отдельный временный каталог и выполните в нём чистую установку и проверки:

```bash
npm ci
npm run check
npm run lint
npm test
npm run build
npm run check:public
```

Для изменений установки или запуска дополнительно проверьте запуск из распакованного архива: на macOS — первый запуск с принудительным переносимым Node.js, повторное использование `.toolchain` и пересборку после изменения исходника; на Windows — `scripts/Test-Windows-Launcher.ps1` через реальный `cmd.exe`. Проверьте, что все тестовые серверы остановлены.

Версия переносимого Node.js и четыре SHA-256 для macOS/Windows зафиксированы в лаунчерах. При обновлении рантайма берите версию и хеши только из официального `https://nodejs.org/dist/…/SHASUMS256.txt`, обновляйте оба лаунчера и `scripts/check-windows-launcher.mjs` синхронно, затем повторяйте чистый запуск. Не заменяйте фиксированные хеши загрузкой контрольной суммы во время установки.

## 9. Опубликуйте

Сначала отправьте ветку и аннотированный тег, затем создайте GitHub Release и приложите ZIP с SHA-256:

```bash
git push origin main
git push origin vX.Y.Z
gh release create vX.Y.Z \
  .release/tochka-opory.zip \
  .release/tochka-opory.zip.sha256 \
  --title "Точка опоры X.Y.Z — короткая пользовательская выгода" \
  --notes-file <подготовленный-файл-описания>
```

Не создавайте draft, если пакет уже проверен и релиз согласован. Не используйте prerelease для обычной стабильной версии.

## 10. Проверьте опубликованный результат

- Откройте страницу релиза и проверьте название, текст и изображения.
- Убедитесь, что тег указывает на релизный коммит.
- Проверьте наличие ZIP и SHA-256.
- Скачайте ZIP по постоянной ссылке `releases/latest` и сверьте контрольную сумму.
- Убедитесь, что ссылка в README ведёт на новую версию.
- Зафиксируйте фактическую публикацию в локальном рабочем файле, не добавляя его в репозиторий.

### Проверка сообщества

- Проверьте актуальность шаблона ошибки, ссылок на Discussions и правил приватности. Не меняйте примеры только ради номера новой версии: шаблон не должен зависеть от текущего релиза.
- При изменении категорий или правил обсуждений вручную обновите приветствие в Discussion #1: его содержимое не хранится в Git.
- Для нового релиза создайте или обновите тему в категории «Новости и релизы», чтобы пользователям было где оставить обратную связь.
- После публикации откройте форму Issue и добавленные ссылки в браузере; тестовый Issue не создавайте.

Если после публикации обнаружена ошибка, не заменяйте старый тег незаметно. Выпустите исправление следующей версией; исключение — отдельно согласованное аварийное изъятие проблемного релиза.
